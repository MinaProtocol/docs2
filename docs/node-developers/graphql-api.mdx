# GraphQL API

import Subhead from "@site/src/components/common/Subhead";

<Subhead>
The interface a running Mina node serves: query the recent chain and the node itself, and submit signed transactions.
</Subhead>

Every Mina daemon serves a [GraphQL](https://graphql.org/) API. Wallets, the [Mina SDKs](/integrations), [o1js](/zkapps/o1js) and the `mina client` command all talk to a node through it. The API is defined by a schema that the daemon generates from its own source code, so the schema and the daemon cannot disagree.

This page is the contract: which schema the current release serves, where to get it as a file, how to reach a node, and what the daemon does and does not expose. The [schema reference](/node-developers/graphql-api/reference/operations) lists every operation and type. [Querying data](/node-operators/validator-node/querying-data) has worked examples.

## Schema version

| | |
|---|---|
| Daemon release | **mina 4.0.3** (Mesa). Releases 4.0.2 and 4.0.3 serve an identical schema |
| Root fields | 41 queries, 29 mutations, 3 subscriptions, 210 types |
| Source of truth | [`graphql_schema.json`](https://github.com/MinaProtocol/mina/blob/4.0.3/graphql_schema.json) at the release tag in the `MinaProtocol/mina` repository |

The daemon is code-first: the OCaml source defines the schema, `make update-graphql` dumps it, and a CI job in the mina repository fails any change that leaves the dump stale. The copy on this site is pinned to the release tag above and a weekly check compares the two, so the reference here describes the schema the released daemon serves, not a development branch.

Changes to the schema arrive with daemon releases. A field that is going away is first marked `@deprecated` with a reason that names its replacement, and it keeps working while it carries that mark. The [deprecated section](/node-developers/graphql-api/reference/deprecated) of the reference lists the current ones: the `wallet` and `ownedWallets` queries and the `addWallet`, `unlockWallet`, `lockWallet`, `deleteWallet` and `reloadWallets` mutations, all replaced by their `account` equivalents. Ask the running node for its own version with the `version` query, which returns the git commit it was built from.

## Fetch the schema as a file

GraphQL has no separate description document like OpenAPI. The schema is the contract, in the two forms the GraphQL specification defines: SDL text and the JSON that an introspection query returns. Both are published here.

| Source | URL | Use it for |
|---|---|---|
| SDL on this site | `https://docs.minaprotocol.com/graphql-api/schema.graphql` | Code generation, AI agents, IDE plugins and documentation tools. Plain text, no authentication |
| Introspection JSON on this site | `https://docs.minaprotocol.com/graphql-api/schema.json` | Tools that read a `schema.json` (`{ "__schema": ... }`) instead of SDL |
| The repository | `https://github.com/MinaProtocol/mina/blob/4.0.3/graphql_schema.json` | The dump the daemon build produced, with its history. Wrapped in `{ "data": ... }` |
| Your own node | `http://localhost:3085/graphql` | The schema that one daemon serves. Introspection is always on |

```sh
# The published schema of the current release, as SDL and as introspection JSON
curl -sO https://docs.minaprotocol.com/graphql-api/schema.graphql
curl -sO https://docs.minaprotocol.com/graphql-api/schema.json

# The schema of your own node, through introspection
npx get-graphql-schema http://localhost:3085/graphql > schema.graphql
```

To generate TypeScript types for your queries with [GraphQL Code Generator](https://the-guild.dev/graphql/codegen), point it at the published URL:

```ts title="codegen.ts"
import type { CodegenConfig } from '@graphql-codegen/cli';

const config: CodegenConfig = {
  schema: 'https://docs.minaprotocol.com/graphql-api/schema.graphql',
  documents: ['src/**/*.graphql'],
  generates: {
    'src/generated/mina.ts': {
      plugins: ['typescript', 'typescript-operations'],
    },
  },
};

export default config;
```

## Reach a node

A daemon serves the API over HTTP on the port that `--rest-port` sets. The default is `3085`, bound to `localhost` only.

| Request | What the daemon does |
|---|---|
| `POST /graphql` with a JSON body `{"query": "...", "variables": {...}}` | Executes a query or a mutation |
| `GET /graphql` from a browser (`Accept: text/html`) | Serves the built-in [GraphiQL](https://github.com/graphql/graphiql) IDE |
| `GET /graphql` with a WebSocket upgrade | Opens a subscription connection (see [Subscriptions](#subscriptions)) |

```sh
curl -s -X POST http://localhost:3085/graphql \
  -H 'Content-Type: application/json' \
  --data '{"query":"{ version networkID daemonStatus { syncStatus blockchainLength } }"}'
```

Two flags change who can reach the node:

| Flag | Effect |
|---|---|
| `--rest-port PORT` | Serve the API on another port. Default `3085` |
| `--insecure-rest-server` | Listen on all addresses instead of `localhost` only |

:::caution
The full API includes mutations that spend from the accounts the daemon has unlocked, stop and reconfigure the node, and change its peers. Exposing it beyond `localhost` lets anyone who can reach the port do those things. Put a firewall or an authenticating proxy in front of the port, or use the limited port below.
:::

### The limited port

For a node that has to answer questions from the Internet, the daemon can serve a second, read-only endpoint:

```sh
mina daemon ... --limited-graphql-port 3086 --open-limited-graphql-port
```

The limited endpoint serves exactly three queries and nothing else: `daemonStatus`, `block` and `version`. No mutations, no subscriptions, no account or pool queries. `--open-limited-graphql-port` makes it listen on all addresses; without that flag it is also bound to `localhost`.

### Public endpoints

o1Labs operates nodes whose full API is open. They are for development and testing, with no uptime guarantee, and they accept signed transactions, which is how the [zkApp tutorials](/zkapps/tutorials/deploying-to-a-network) deploy.

| Network | Endpoint |
|---|---|
| Devnet | `https://devnet-plain-1.gcp.o1test.net/graphql` |
| Mainnet | `https://mainnet-plain-1.gcp.o1test.net/graphql` |

For production, run your own node, or use a provider's endpoint.

## What the daemon exposes

The daemon keeps only the blocks in its transition frontier, the last `k` blocks (290). `bestChain`, `block` and the transaction queries answer from that window. For anything older, use an [archive node](/node-operators/archive-node) through the [Archive Node API](/node-operators/data-and-history/archive-node-api). The [Integrations](/integrations) page compares the data paths.

### Queries

Queries read the node and the recent chain. The ones most integrations use:

| Query | Returns |
|---|---|
| `daemonStatus` | Sync status, chain id, block height, peers, uptime and the node's configuration |
| `syncStatus` | The sync status alone, the cheapest health check |
| `account(publicKey:, token:)` | Balance, nonce, delegate, permissions and zkApp state of one account, at the best tip |
| `bestChain(maxLength:)` | The most recent blocks on the best chain, newest last, with their transactions |
| `block(stateHash:)` / `block(height:)` | One block in the frontier |
| `pooledUserCommands`, `pooledZkappCommands` | The transaction pool, for fee estimation and for finding a transaction that is not yet in a block |
| `transactionStatus(payment:)` / `transactionStatus(zkappTransaction:)` | Whether a transaction is `PENDING`, `INCLUDED` or `UNKNOWN` |
| `genesisConstants`, `networkID`, `version` | What the node is and what it was built from |

Every query, with its arguments and the types it returns, is in the [queries reference](/node-developers/graphql-api/reference/operations/queries).

### Mutations

Mutations change the node or submit transactions. `sendPayment`, `sendDelegation` and `sendZkapp` take a transaction that was signed elsewhere, with [mina-signer](/node-operators/mina-signer) or o1js, so a node that only relays transactions never holds a key. The other mutations manage accounts the daemon stores, set the SNARK worker and its fee, set the coinbase receiver, add peers and manage logs. All of them are in the [mutations reference](/node-developers/graphql-api/reference/operations/mutations).

### Subscriptions

Three subscriptions push events to a client:

| Subscription | Fires when |
|---|---|
| `newBlock(publicKey:)` | The node adds a block to its frontier, optionally only blocks a given producer made |
| `newSyncUpdate` | The sync status changes |
| `chainReorganization` | The best tip moves to a block that is not a child of the previous one |

Subscriptions run only over WebSocket. A subscription sent as an HTTP `POST` is rejected with `Subscriptions are only supported via websocket transport`. The daemon speaks the [subscriptions-transport-ws](https://github.com/apollographql/subscriptions-transport-ws) protocol (subprotocol name `graphql-ws`), the one the bundled GraphiQL uses. Clients that implement only the newer `graphql-transport-ws` protocol of the [graphql-ws](https://github.com/enisdenjo/graphql-ws) library do not connect; most of them can be configured to fall back to the older protocol.

```graphql
subscription {
  newBlock {
    creator
    stateHash
    protocolState {
      consensusState {
        blockHeight
      }
    }
  }
}
```

## Encodings

A few conventions apply across the schema. Scalars are documented individually in the [scalars reference](/node-developers/graphql-api/reference/types/scalars).

- Amounts and fees (`Amount`, `Fee`) are strings of nanomina: `"1000000000"` is 1 MINA. An account's `balance` is an object whose `total`, `liquid` and `locked` fields are `Balance` strings in the same unit.
- Public keys are Base58Check strings beginning with `B62`. Transaction hashes, state hashes and ledger hashes are Base58Check strings too.
- `memo` on a transaction is Base58Check encoded, not plain text.
- Block heights (`Length`), slots (`Globalslot`, `Slot`) and epochs (`Epoch`) are strings. A transaction's `nonce` is an `Int`.
