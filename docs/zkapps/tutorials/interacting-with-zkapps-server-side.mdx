# Interacting with zkApps server-side

While user-facing zkApps can be written for the browser, sometimes it is useful to interact with a zkApp server-side or on your own machine. For example, when initializing a zkApp using programmatically generated information, deploying a zkApp in custom ways, or writing scripts that create transactions depending on real-world (periodically updating an on-chain value with signed data, like a keeper for an oracle) or on-chain events.

Interacting with zkApps server-side is useful for some use cases. For example, if you need to create a custom account for your zkApp to deploy a zkApp to a different key than the fee payer key. You can programmatically parameterize a zkApp before you initialize it. You can even create a smart contract programmatically for users as part of an application.

## Prerequisites

Ensure your environment meets the [Prerequisites](/zkapps/tutorials#prerequisites) for zkApp Developer Tutorials. o1js 3 requires Node.js 22.19.5 or later.

The script on this page connects to Devnet. Before you start, complete [Tutorial 3: Deploy to a Live Network](deploying-to-a-network), which reuses the smart contract `Square` from [Tutorial 1: Hello World](hello-world). Tutorial 3 gives you these items, which this script uses:

- A deploy alias in `config.json`, made with the `zk config` command
- A fee payer account that has tMINA from the faucet
- A zkApp account where `zk deploy` deployed the `Square` contract

To try the same flow without a network, a funded account or key files, go to [Run it without a network](#run-it-without-a-network).

The [example project](https://github.com/MinaProtocol/docs2/tree/main/examples/zkapps/interacting-with-zkApps-server-side) uses o1js `^3.0.0`. CI builds it on every pull request, and runs and tests its local version (`src/local.ts`). CI does not run the Devnet script (`src/main.ts`), because that script needs funds and keys.

### Connect to a remote network

Set the active instance to the remote network of the deploy alias. Earlier tutorials set the active instance to a simulated local blockchain, which is fast for development but only available on your local machine and is not decentralized.

The connection is made through the GraphQL endpoint exposed by a Mina node. For the `devnet` alias of Tutorial 3, the endpoint is `https://devnet-plain-1.gcp.o1test.net/graphql`. By connecting to the remote Devnet network, you can provide smart contracts that are globally accessible and provide strong guarantees around state due to both Mina's decentralization and its succinct state proof.

The deploy alias also sets the transaction fee, in MINA. Transaction fees in code are declared in nanomina, so the script converts the value. For the fee of `0.1` from Tutorial 3, the result is 100,000,000 nanomina:

### Public/private key pairs

You already generated two key pairs when you ran the `zk config` command in [Tutorial 3: Deploy to a Live Network](/zkapps/tutorials/deploying-to-a-network#deploy-alias):

- The zkApp key pair, in `keys/devnet.json`. `zk deploy` deployed the `Square` contract to this account.
- The fee payer key pair, in `${HOME}/.cache/zkapp-cli/keys/03-deploy.json`. You funded this account at the faucet.

The deploy alias in `config.json` holds the path of each file, as `keyPath` and `feepayerKeyPath`. Public and private keys in Mina are commonly stored in Base58 for easy readability. In Mina, public keys start with `B62` and private keys start with `EK` for easy differentiability.

Then the script compiles the smart contract and makes sure that the zkApp is deployed:

#include_code deploy examples/zkapps/interacting-with-zkApps-server-side/src/main.ts ts title="src/main.ts"

The `deploy()` function from `utils.ts` first reads the zkApp account. You deployed the contract with `zk deploy` in Tutorial 3, so the account has a verification key: `deploy()` shows that the zkApp is found deployed, and does not send a transaction. If the account has no verification key, `deploy()` sends a deploy transaction, signed with the fee payer key and the zkApp key. To see how this works, see the code in [utils.ts](https://github.com/MinaProtocol/docs2/blob/main/examples/zkapps/interacting-with-zkApps-server-side/src/utils.ts).

Then the script calls `loopUntilAccountExists()` with `isZkAppAccount: true`. This checks that the account exists and that it has zkApp state, which shows that the zkApp was deployed successfully.

After the zkApp has been deployed, the script fetches the current value of `zkapp.num` (the on-chain state defined on the `SmartContract`) and shows it. If you did not update the contract after Tutorial 3, the value is `3`, because that's how it is set in the smart contract's `init()` function. The `init()` function is called automatically during the first deploy (not during re-deploys).

### Send an update transaction

Finally, here is code that sends an update transaction. It calls `update()` with the square of the current value of `num`:

#include_code update examples/zkapps/interacting-with-zkApps-server-side/src/main.ts ts title="src/main.ts"

To send an update transaction, perform the following steps:

1. Construct the transaction with `Mina.transaction`. This is where you call `zkapp.update()`, the custom method defined on the smart contract.
2. Create a proof of the transaction. This can take up to a minute.
3. Sign the transaction and send it to the network.

When sending the transaction using `transaction.send()`, an object called `pendingTransaction` is returned and provides information about how the transaction went and waits for inclusion in a block:

#include_code wait-for-inclusion examples/zkapps/interacting-with-zkApps-server-side/src/main.ts ts title="src/main.ts"

This code uses several functionalities of the pending transaction:

- `pendingTransaction.status` indicates the initial processing status of the transaction, with `pending` signifying that the transaction has been accepted for processing by the network, and `rejected` indicating that the transaction was immediately deemed invalid and rejected by the GraphQL endpoint.
- `pendingTransaction.hash` is the transaction hash that you can use to look up the transaction in a block explorer.
- `pendingTransaction.wait()` is especially useful as it returns a promise that resolves when a transaction is included into a block, and rejects when the transaction fails. This takes several minutes, so you might not want to block the main thread on this in a real application.

Finally, after the transaction was successfully applied on the Mina blockchain, you can double-check that your state was updated by fetching it again with `zkapp.num.fetch()`.

## Run it without a network

The Devnet script needs a funded account, a key file and a live node, so you
cannot try it until you have all three, and neither can CI. The example
project in this repository carries a second entry point, `src/local.ts`, that
runs the same flow against a local blockchain:

```sh
cd examples/zkapps/interacting-with-zkApps-server-side
npm install
npm start
```

The two addresses change on each run, because the test accounts and the zkApp key are random:

```text
fee payer : B62q...
zkApp     : B62q...

deploying...
current value of num is 3

updating num to its square...
updated state! 9

rejecting an update that is not the square...
rejected, as it should be: Field.assertEquals(): 10 != 81
state is still 9
```

It keeps what this page teaches — deploying the zkApp to a key that is **not**
the fee payer's, and driving it from a script — and drops only what needs a
network. In particular there is no `loopUntilAccountExists`. A remote node is
eventually consistent, so the account is not readable the moment the
transaction is sent; a local blockchain applies the transaction as it is sent,
so there is nothing to poll for:

#include_code deploy examples/zkapps/interacting-with-zkApps-server-side/src/local.ts ts title="src/local.ts"

`npm test` asserts the same ground, including the account creation fee the fee
payer pays for the zkApp account and the rejection of an update that is not
the square.
