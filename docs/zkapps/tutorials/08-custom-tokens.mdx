# Tutorial 8: Custom Tokens

In this tutorial, you learn to create custom tokens, and to write a zkApp that consumes a custom token: it takes deposits of the token and holds them.

Mina comes with native support for custom tokens. Each account on Mina can also have tokens associated with it.

To create a new token, one creates a smart contract, which becomes the manager for the token, and uses that contract to set the rules around how the token can be minted, burned, and sent.

The manager account may also set a token symbol for its token, such as in this example, `MYTKN`. Uniqueness is not enforced for token names. Instead the public key of the manager account is used to identify tokens.

In this tutorial, you review smart contract code that creates and manages new tokens. Then you review a zkApp that holds a custom token. See [Consume tokens in a zkApp](#consume-tokens-in-a-zkapp).

The full example code is provided in the [08-custom-tokens/src/](https://github.com/MinaProtocol/docs2/tree/main/examples/zkapps/08-custom-tokens/src) example files.

For reference, a more extensive example, including all the ways to interact with token smart contracts, is provided in [token.test.ts](https://github.com/o1-labs/o1js/blob/main/src/lib/mina/v1/token.test.ts).

## Concepts

Before you read the contract, learn the three objects that every custom token on Mina uses: the token manager, the token id, and the token account. Then learn the approval mechanism, which is how the token manager controls every change to a token balance.

The [tokenConcepts.test.ts](https://github.com/MinaProtocol/docs2/blob/main/examples/zkapps/08-custom-tokens/src/tokenConcepts.test.ts) test file in the example project checks most of the statements in this section on a local blockchain.

### Token manager

The token manager is the zkApp account that owns a token. In o1js, you write a token manager as a class that extends `TokenContract`. The token manager can:

- Set a token symbol for its token, such as `MYTKN`. The token symbol is not unique. Two token managers can set the same symbol and still manage two different tokens.
- Mint tokens. Minting adds tokens to the balance of an account. In o1js, `this.internal.mint()` does this.
- Burn tokens. Burning removes tokens from the balance of an account. In o1js, `this.internal.burn()` does this, and it requires a signature from the account that loses the tokens. A balance cannot go below zero, so an account cannot burn or send more tokens than it holds.
- Approve transfers. Any account that holds the token can start a transfer, but the token manager must approve it. See [Approval mechanism](#approval-mechanism).

`TokenContract.deploy()` sets the `access` permission of the token manager account to `proofOrSignature()`, and requires that the account is new. Without this permission, anyone can mint the token without the token manager.

### Token id

A token id is a field element that identifies a token. The token id is derived from the public key of the token manager, so each token manager has exactly one token id. That is why the token symbol does not need to be unique.

To get the token id of a token manager, call `deriveTokenId()` on the contract:

```ts
const tokenId = token.deriveTokenId();
```

This is the same value as `TokenId.derive(token.address)`. The MINA token has the token id `TokenId.default`, which is `1`.

`TokenId.derive()` also takes the token id of the token manager account as a second argument, which is `TokenId.default` when you do not supply it. For a token manager that is a normal MINA account, like the one in this tutorial, the two calls give the same value.

### Token account

An account on Mina is identified by a public key _and_ a token id. A token account is an account whose token id is the id of a custom token. Its balance is in that token, not in MINA.

So one public key can have many accounts: one MINA account and one token account for each token that it holds. They are separate accounts. When you mint tokens to a public key, its MINA balance does not change.

To read a token balance, give the token id:

```ts
Mina.getBalance(address, tokenId); // the token balance
Mina.getBalance(address); // the MINA balance
```

A token account is created the first time that its public key receives the token. The public key does not need a MINA account. Creating a token account costs the account creation fee, the same as creating a MINA account. Some account in the transaction must pay it, usually with `AccountUpdate.fundNewAccount()`. If no account pays it, the transaction fails with `Invalid fee excess`. Later transactions to the same token account do not pay the fee again.

### Approval mechanism

Every change to a token account is an account update with that token id. The Mina protocol accepts such an account update only when it is a child of the token manager's account update in the same transaction, or a deeper descendant that inherits the token permission from its parent. A top-level account update that uses a custom token id fails. On a local blockchain, the error is `Top-level account update can not use or pass on token permissions` when the token account exists. When the account update creates the token account, the error is `Token_owner_not_caller`. So a token holder cannot move tokens without the token manager, even with a valid signature.

The token manager approves account updates in two ways:

- Its own methods create the account updates, as `this.internal.mint()`, `this.internal.burn()` and `this.internal.send()` do. The rules in the method are the rules of the token.
- It approves account updates that other code created. `TokenContract` leaves the `approveBase()` method for you to define. It receives the account updates as an `AccountUpdateForest` and must fail if it does not approve them. The helpers `transfer()`, `approveAccountUpdate()` and `approveAccountUpdates()` all put the account updates into a forest and call `approveBase()`.

`checkZeroBalanceChange()` is the most common implementation of `approveBase()`. It proves that the token balance changes of the approved account updates sum to zero, so an approved transaction cannot create tokens. `approveBase()` can check at most `TokenContract.MAX_ACCOUNT_UPDATES` account updates, which is `9` by default.

Make `approveBase()` a `@method`, so that the token manager can prove its approval. If `approveBase()` is not a `@method`, `transfer()` does not add the token account updates to the transaction, and the transaction moves no tokens. When `approveBase()` is a `@method`, any token holder can call `transfer()`, and signs only for the account that sends the tokens:

### Rules in approveBase()

Any account can call a `@method`. So when `approveBase()` is a `@method`, it must enforce every rule of the token. If it only calls `checkZeroBalanceChange()`, a token holder can use `transfer()` to send tokens to an address that `sendTokens()` refuses.

## Consume tokens in a zkApp

A token manager makes and moves its token. Other zkApps can also use the token. For example, a zkApp can take a deposit of a token from a user, hold the token, and pay it back later. In this section, you review `TokenVault`, a zkApp that does this with the `MYTKN` token of `BasicTokenContract`.

The rules of `TokenVault` are:

- Any account can deposit `MYTKN` into the vault.
- Only the owner of the vault can withdraw.
- The owner cannot withdraw more than the total deposited.

A full copy of [TokenVault.ts](https://github.com/MinaProtocol/docs2/blob/main/examples/zkapps/08-custom-tokens/src/TokenVault.ts) is provided. The [TokenVault.test.ts](https://github.com/MinaProtocol/docs2/blob/main/examples/zkapps/08-custom-tokens/src/TokenVault.test.ts) and [TokenVault.proofs.test.ts](https://github.com/MinaProtocol/docs2/blob/main/examples/zkapps/08-custom-tokens/src/TokenVault.proofs.test.ts) test files check the statements in this section on a local blockchain. The second file creates real proofs.

### The vault is on a token account

A zkApp holds a custom token in a token account. A token account is identified by a public key and the token id (see [Token account](#token-account)). So the vault is the account (vault address, token id of `BasicTokenContract`). It is not the MINA account at the vault address. The MINA account at the same address is a different account, and it does not need to exist.

To make a contract object for a token account, give the token id as the second argument of the constructor:

```ts
const vault = new TokenVault(vaultAddress, token.deriveTokenId());
```

Without the second argument, the contract object is for the MINA account at that address. Each account update that a `TokenVault` method makes is then on the token account. o1js sets `mayUseToken` of these account updates to `parentsOwnToken`. This flag tells the protocol that the parent account update in the transaction must be the account update of the token manager.

`TokenVault` extends `SmartContract`, not `TokenContract`, because it does not manage a token. It has two state variables: the owner, and the total deposited:

#include_code vault-structure examples/zkapps/08-custom-tokens/src/TokenVault.ts ts title="src/TokenVault.ts"

`deploy()` takes the owner as an argument and sets the state. It also sets these permissions on the vault account:

- `receive: Permissions.proof()`. Only a proof of a vault method can add tokens to the vault. Without this permission, any account can send tokens to the vault with `transfer()`, and `totalDeposited` does not count them. A transfer that bypasses `deposit()` fails with `Update_not_permitted_balance`.
- `setPermissions: Permissions.impossible()` and `setVerificationKey: Permissions.VerificationKey.impossibleDuringCurrentVersion()`. Nobody can change the permissions or the code of the vault after deployment, not even the holder of the vault private key. Without these permissions, the holder of the vault private key can set `send` to `signature()` and take the tokens without `withdraw()`.

The default permissions of a zkApp already set `send` and `editState` to `proof()`. So only a proof of `withdraw()` can take tokens out of the vault, and only the vault methods can change its state.

### Deploy the vault with the approval of the token manager

The vault account is a token account, so its deploy account update uses the token. The token manager must approve every account update that uses its token, the deploy update too. Thus, deploy the vault and give its account update to `approveAccountUpdate()` of the token manager in the same transaction:

#include_code vault-deploy examples/zkapps/08-custom-tokens/src/main.ts ts title="src/main.ts"

`approveAccountUpdate()` calls `approveBase()` of `BasicTokenContract`. `approveBase()` calls `checkZeroBalanceChange()`. The deploy update does not change a balance, so `BasicTokenContract` approves it.

The deploy creates one new account, the vault token account. `AccountUpdate.fundNewAccount()` pays the account creation fee for it.

If you deploy the vault without `approveAccountUpdate()`, the transaction fails with `Token_owner_not_caller`, because the vault token account does not exist yet.

A token manager decides which zkApps it approves. `BasicTokenContract` approves each account update when the balance changes sum to zero, so it approves any zkApp on its token. A token manager can be more strict. For example, it can approve only zkApps with a known verification key. For an example, see [Approve a deployment on a token account](/zkapps/tutorials/advanced-account-updates#approve-a-deployment-on-a-token-account) in Tutorial 11.

### Deposit tokens

To deposit, call `deposit()` and then `transfer()` of the token manager in the same transaction. Give `vault.self`, the account update that `deposit()` made, as the receiver:

#include_code vault-deposit examples/zkapps/08-custom-tokens/src/main.ts ts title="src/main.ts"

`transfer()` makes an account update that takes the amount from `bob`, and puts the two account updates in a forest. Then it calls `approveBase()`. The account updates become children of the token manager account update, so the protocol accepts them. `checkZeroBalanceChange()` proves that the balance changes sum to zero: `bob` loses what the vault gets. `bob` signs the transaction, because his account update sends tokens and requires a signature.

These conditions apply:

- The amount that you give to `transfer()` must be the amount that you give to `deposit()`. `transfer()` sets the balance change of the vault account update again. If the two amounts are different, `tx.prove()` fails, because o1js cannot prove `deposit()` for the changed account update. A local blockchain with `proofsEnabled: false` does not check proofs, so it accepts this transaction. Test this condition with proofs.
- If you call `deposit()` without the token manager, the vault account update is a top-level account update that uses the token. On a local blockchain, the transaction fails with `Top-level account update can not use or pass on token permissions`.
- If the token manager approves only `vault.self`, with no account that pays the tokens, the balance changes do not sum to zero. `checkZeroBalanceChange()` fails with `Field.assertEquals(): 1000 != 0` for a deposit of 1000.

To withdraw, call `withdraw()` and then `transfer()` of the token manager. Give `vault.self` as the sender:

The vault account update does not need a signature from the vault private key. Its authorization is the proof of `withdraw()`. The owner signs the transaction, because `this.sender.getAndRequireSignature()` makes an account update that requires the signature of the sender.

A withdrawal fails in these conditions:

- The sender is not the owner. The error is `only the owner can withdraw`.
- The amount is more than `totalDeposited`. The error is `cannot withdraw more than the total deposited`.
- The token manager does not approve the account updates. On a local blockchain, the error is `Top-level account update can not use or pass on token permissions`.
