# Tutorial 5: Common Types and Functions

In previous tutorials, you learned how to deploy smart contracts to the network and interact with them from a React UI and NodeJS.

In this tutorial, you learn about types you can use when building with o1js. Earlier tutorials mostly use the `Field` type. o1js provides other higher-order types built from Fields that are useful for zkApp development and expand the possibilities for more applications.

The [example project](https://github.com/MinaProtocol/docs2/tree/main/examples/zkapps/05-common-types-and-functions/src) includes a [main.ts](https://github.com/MinaProtocol/docs2/blob/main/examples/zkapps/05-common-types-and-functions/src/main.ts) file that shows all of the concepts presented in this tutorial, along with smart contracts showing more advanced usage of some of the concepts, particularly Merkle Trees.

## More Advanced Types

Four advanced types are:

- [CircuitString](https://docs.o1labs.org/o1js/api-reference/classes/CircuitString)
- [PrivateKey](https://docs.o1labs.org/o1js/api-reference/classes/PrivateKey)
- [PublicKey](https://docs.o1labs.org/o1js/api-reference/classes/PublicKey)
- [Signature](https://docs.o1labs.org/o1js/api-reference/classes/Signature)

All arguments passed into smart contracts must be arguments o1js can consume. You cannot pass normal strings. Instead, you must pass in strings that are wrapped to be compatible with circuits. This is accomplished with `Struct`.

The default `CircuitString` has a maximum length of 128 characters because o1js types must be fixed length. However, the `CircuitString` API abstracts this restriction away and can be used like a dynamic length string with the maximum length caveat.

You can create custom types to build your own strings, modified to whatever length you want.

## Assertions and Constraints

o1js functions are compiled to generate circuits.

When a transaction is proven in o1js, the proof is that the program logic is computed according to the written program, and all assertions are holding true.

In previous tutorials, you learned `a.assertEquals(b)`. The `.assertTrue()` is available on the Bool class.

Circuits in o1js have a fixed maximum size. Each operation performed in a function counts towards this maximum size. This maximum size is equivalent to:

- about 5,200 hashes on two fields
- about 2,600 hashes on four fields
- about `2^17` field multiplies
- about `2^17` field additions

If a program is too large to fit into these constraints, it can be broken up into multiple recursive proof verifications. See [Recursion](https://docs.o1labs.org/o1js/advanced-concepts/recursion).

:::

## Provable data structures

A circuit has a fixed size. Thus, a smart contract method cannot take a JavaScript array or a JavaScript `Map` of any length. A method can take only a _provable type_: a type that o1js can convert to a fixed number of field elements. o1js 3.0.0 has these provable data structures:

- A fixed-size array, made with `Provable.Array(type, length)` or with a `Struct`, such as `Points8` in [Struct](#struct).
- `DynamicArray`: an array with a fixed capacity and a length that can change.
- `MerkleList`: a list of any length, which the circuit sees as one hash.
- `MerkleTree` and `MerkleWitness`: values at index positions. See [Merkle Trees](#merkle-trees).
- `MerkleMap` and `MerkleMapWitness`: values by key. See [Merkle Map](#merkle-map).
- `IndexedMerkleMap`: values by key, with fewer constraints than `MerkleMap`.

A _commitment_ is one field element, such as a hash or a Merkle root, that identifies all of the data. Usually, a smart contract stores only the commitment in its on-chain state. The caller keeps the full data off chain and gives it to the method as an argument. The method makes sure that the data agrees with the commitment on chain, changes the data, and stores the new commitment.

### Which structure for which job

The _rows_ column shows the size of the circuit of each method in the example project. It is the number that `analyzeMethods()` reports in o1js 3.0.0. A method that only sets one state field, such as `initState`, takes 614 rows. Thus, most of the rows of a small method do not come from the data structure.

| Structure | Use it when | Size limit | What the method gets | What goes on chain | Rows in the example |
| --- | --- | --- | --- | --- | --- |
| `Provable.Array`, `Struct` | You always have exactly `n` values. | `n`, fixed | all `n` values | the values, or their hash | not measured |
| `DynamicArray` | You have from 0 to `capacity` values, and the method reads all of them or reads by index. | `capacity` less than 2<sup>16</sup> | all `capacity` slots and the length | nothing, or a hash that you calculate | `addAll`: 742, `pick`: 707 (capacity 8) |
| `MerkleList` | You have a list of unknown length that a method reads in order, for example a queue of tasks. | no limit on the list; `forEach(n)` reads at most `n` elements | 1 field: the hash | the hash | `push`: 628, `pop`: 628, `sum`: 686 (4 steps) |
| `MerkleTree` | You have values at index positions. | 2<sup>(height-1)</sup> leaves | a witness of `height - 1` hashes | the root | `update`: 1,307 (height 20) |
| `MerkleMap` | Existing code uses it. | height fixed at 256 | a witness | the root | `update`: 10,591 |
| `IndexedMerkleMap` | You need values by key, or you must prove that a key is not in the map. | 2<sup>(height-1)</sup> leaves, height at most 52 | 2 fields, plus the map data as an unconstrained value | the root | `insert`: 2,621, `update`: 1,613 (height 33) |

An _unconstrained_ value is data that the prover gives to the circuit without a proof. The method must check it against a constrained value, for example against the root on chain.

### IndexedMerkleMap

An `IndexedMerkleMap` is a key-value map in a Merkle tree. Each leaf holds a key, a value, and the next larger key in the map. Thus, the leaves make a sorted linked list. Because of this list, the map can prove that a key is not in the map: it shows the leaf with the next smaller key, and that leaf points to a larger key.

In o1js 3.0.0, import `IndexedMerkleMap` directly from `o1js`. It is not in the `Experimental` namespace. Make a class for one height:

#include_code indexed-merkle-map examples/zkapps/05-common-types-and-functions/src/main.ts ts title="src/main.ts"

The output:

```
value for key 100: 50
key 101 is in the map: false
Fields in Map33: 2
second insert of key 100: rejected
```

These are the rules of the map:

- A new map contains the key `0` with the value `0`. This entry uses one of the 2<sup>(height-1)</sup> leaves.
- `insert(key, value)` fails if the key is already in the map.
- `update(key, value)` fails if the key is not in the map. It returns the old value.
- `set(key, value)` does an insert or an update. It costs more constraints than `insert()` or `update()`.
- `get(key)` fails if the key is not in the map.
- `getOption(key)` returns an `Option`: a provable type with an `isSome` Bool and a `value`. `isSome` is false if the key is not in the map. Then `value` is unconstrained, so read it with `orElse(default)`. The o1js API reference says that `getOption()` takes about two times the constraints of `get()`.
- `map.root` is the hash of the internal Merkle root and the number of entries. Store `map.root` on chain.

The map goes into a smart contract method as an argument. The contract stores only the root:

#include_code indexed-merkle-map-contract examples/zkapps/05-common-types-and-functions/src/IndexedMerkleMapContract.ts ts title="src/IndexedMerkleMapContract.ts"

The method changes a `clone()` of the map, not the argument. In o1js 3.0.0, `Mina.transaction()` can run the method body more than one time, and the argument shares its unconstrained data with the map of the caller. If the method changes the argument, the first run adds the key to the data of the caller but not to its root. The second run then fails with `Invalid low node (root)`. The tests of the example project find this error.

The caller sends the transaction, and then makes the same change to its own map:

#include_code indexed-merkle-map-interaction examples/zkapps/05-common-types-and-functions/src/main.ts ts title="src/main.ts"

The output:

```

```

### MerkleList

A `MerkleList` is a list that the circuit sees as one hash. Each `push()` hashes the old hash with the new element. `popExn()` removes the element that was pushed last, so the list is a stack. Because the method gets only the hash, the list can have any length.

Use a `MerkleList` when:

- The length of the data is not known when you write the contract.
- The method reads the elements in order, not by index.

`forEach(n, callback)` always takes `n` steps, so its cost is `n` times the cost of one step. It fails if the list has more than `n` elements. After the last element, the callback gets dummy elements with `isDummy` set to true.

#include_code merkle-list examples/zkapps/05-common-types-and-functions/src/main.ts ts title="src/main.ts"

The output:

```

Fields in the list: 1

`popExn()` fails on an empty list. `pop()` does not fail on an empty list: it returns a dummy element. `popOption()` returns an `Option`.

### DynamicArray

A `DynamicArray` has a fixed _capacity_ and a _length_ from 0 to the capacity. The circuit always holds all capacity slots plus one field for the length. The slots after the length can hold any value that the prover gives.

Use a `DynamicArray` when:

- The data is short and its length changes, for example from 0 to 8 scores.
- The method must read elements by index, or must read all elements.

A read at a variable index adds one constraint for each slot, so the cost grows with the capacity. For long data, use a `MerkleList` or a Merkle tree.

#include_code dynamic-array examples/zkapps/05-common-types-and-functions/src/main.ts ts title="src/main.ts"

The output:

```

Fields in Scores: 9

### Not on this page

o1js 3.0.0 has more provable types that hold data. This tutorial does not show them:

- `Bytes` and `UInt8`: fixed-size byte arrays for hash functions such as SHA-256 and Keccak.
- `Experimental.OffchainState` and `Experimental.BatchReducer`: APIs that keep a map or a list off chain and settle it with actions. See [Tutorial 6](offchain-storage) for off-chain storage.

## Test it

The example project in this repository carries two test suites for the code on
this page:

```sh
cd examples/zkapps/05-common-types-and-functions
npm install
npm test
```

`CommonTypes.test.ts` asserts each value that the console-output blocks on this
page print, from `num1 === num2: true` to `value for key 100: 50`. It also runs
three contracts on a local blockchain:

- `BasicMerkleTreeContract` accepts an increment of `9` and **rejects** an
  increment of `10`. After an update, the contract root and the local tree
  root are equal.
- `BasicMerkleMapContract` adds `5` to key `100` and **rejects** an increment
  of `10` and a witness for a different key. After an update, the contract
  root and the local map root are equal.
- `LedgerContract` moves `12` to an existing recipient and to a new recipient.
  It **rejects** a transfer signed by a different key, a transfer of the full
  balance, and a new recipient that claims a balance that is not `0`.

`DataStructures.test.ts` covers the provable data structures:

- `IndexedMerkleMap` **rejects** a second insert of the same key, an update of
  a missing key, `get()` of a missing key, more keys than 2<sup>(height-1)</sup>
  leaves, and a height of 53. `IndexedMerkleMapContract` keeps the same root as
  the local map, does not change the map of the caller, and **rejects** a map
  that does not match the root on chain. Its methods take at least 4 times fewer
  rows than the `MerkleMap` update.
- `MerkleListContract` pops the element that was pushed last, adds up a list of
  3 elements, and **rejects** a pop from an empty list, a sum of a list longer
  than `MAX_SUM_LENGTH`, and a list that does not match the hash on chain.
- `DynamicArrayContract` adds up only the real elements, also when the empty
  slots hold other values, and **rejects** an index that is not less than the
  length. `Scores.from()` **rejects** more elements than the capacity.

`main.ts` compiles all six contracts and creates real proofs, so it takes
several minutes. The test suites turn proofs off and are much faster.
