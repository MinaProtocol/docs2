# Archive Node API

import Tabs from '@theme/Tabs';
import TabItem from '@theme/TabItem';
import Subhead from "@site/src/components/common/Subhead";

<Subhead>
A GraphQL service over an archive node database — the supported way for zkApps, explorers, and indexers to read Mina's history.
</Subhead>

An [archive node](/node-operators/archive-node) stores Mina's history in a Postgres database, but it exposes no public API of its own. The [Archive Node API](https://github.com/o1-labs/Archive-Node-API) closes that gap: it is a read-only GraphQL server that you point at an existing archive node database and query for blocks, events, actions, and transactions.

It does **not** run an archive node. You need one already syncing, or a snapshot of its database, before this service has anything to serve.

## Choose a data path

Four ways to read Mina data. They are not interchangeable — pick by what you are building.

| You need | Use | Why |
|---|---|---|
| Current network state, recent blocks, sending transactions | [Daemon GraphQL](/node-operators/validator-node/querying-data) | The daemon keeps only the last k blocks (currently 290) |
| zkApp events and actions, block and transaction history | **Archive Node API** | Purpose-built for o1js and zkApp developers |
| Exchange integration — deposits, withdrawals, balances | [Rosetta API](/node-operators/data-and-history/rosetta) | A standardized cross-chain interface exchanges already support |
| Arbitrary analytical queries over the full schema | The archive Postgres directly | No API constrains your query shape — and none protects the database |

The Archive Node API and Rosetta read the *same* archive database. Running both against one database is normal.

## Architecture

| Component | Default port | Role |
|---|---|---|
| Mina daemon | 8302 (P2P), 3085 (GraphQL) | Syncs with the network |
| `mina-archive` process | 3086 | Receives blocks from the daemon, writes them to Postgres |
| PostgreSQL | 5432 | Stores the history |
| **Archive Node API** | 8080 | Serves GraphQL over that Postgres |

The API holds a connection pool to Postgres and issues read-only queries. It has no write path, no keys, and no daemon connection of its own.

## The query surface

Eight root fields. The authoritative definition is the [schema](/node-operators/data-and-history/archive-node-api-schema) page, which also gives the schema as a file to download. The generated [schema reference](/node-operators/data-and-history/archive-node-api/reference/operations) has one page per query and per type.

| Query | Returns |
|---|---|
| `events(input:)` | Events emitted by a zkApp account, filtered by address, token, block range, and chain status |
| `actions(input:)` | Actions dispatched from a zkApp account, optionally bounded by action state |
| `blocks(query:, limit:, sortBy:)` | Blocks by height or date range, with transaction detail |
| `networkState` | The archive's maximum canonical and pending block heights |
| `verificationKeyUpdates(input:)` | Applied account updates that set a given verification key, over a required block range |
| `zkappCommands(input:)` | zkApp commands and their account updates over a block range, optionally filtered by account and token. Off unless `ENABLE_ZKAPP_COMMANDS_QUERY=true` |
| `userCommands(input:)` | Payments and delegations of one account over a required block range, whether the account is the fee payer, the source or the receiver. Off unless `ENABLE_USER_COMMANDS_QUERY=true`. Added in schema 2.1 |
| `schemaVersion` | The `MAJOR.MINOR` version of the schema this server speaks. Always served |

The examples below run against your own instance from [Quick start](#quick-start). The addresses, heights and hashes are real Devnet values, so they return data on a Devnet archive, and the responses shown are what a Devnet archive returned. Block ranges are `from` inclusive and `to` exclusive on every query.

### Handshake

The first query a client sends. `schemaVersion` tells you which contract the server speaks, and `networkState` tells you how far the archive has synced. A block becomes canonical when it is 290 blocks (k) below the tip, so the two heights differ by about 290:

```graphql
query {
  schemaVersion
  networkState {
    maxBlockHeight {
      canonicalMaxBlockHeight
      pendingMaxBlockHeight
    }
  }
}
```

### Actions

Replace `address` with your zkApp's public key in these two examples.

Actions folded from a checkpoint, which is what an o1js reducer does. The `fromActionState` below is the initial action state of every account, so this request starts from the zkApp's first action. In a reducer loop, pass the last action state you processed instead:

```graphql
query {
  actions(
    input: {
      address: "B62q..."
      status: CANONICAL
      fromActionState: "25079927036070901246064867767436987657692091363973573142121686150614948079097"
    }
  ) {
    blockInfo {
      height
      stateHash
    }
    transactionInfo {
      hash
      status
    }
    actionState {
      actionStateOne
      actionStateTwo
      actionStateThree
      actionStateFour
      actionStateFive
    }
    actionData {
      accountUpdateId
      data
    }
  }
}
```

Actions between two checkpoints, inside a block range. Both action-state bounds are inclusive. Use this when a reducer has already settled up to `endActionState`:

```graphql
query {
  actions(
    input: {
      address: "B62q..."
      from: 470000
      to: 480000
      fromActionState: "25079927036070901246064867767436987657692091363973573142121686150614948079097"
      endActionState: "<action state after the last processed action>"
    }
  ) {
    blockInfo {
      height
    }
    actionState {
      actionStateOne
    }
    actionData {
      data
    }
  }
}
```

`actionStateOne` is the action state after the block's actions were applied. `actionStateTwo` to `actionStateFive` are the four earlier states that the account keeps, which a reducer uses to find its checkpoint again after a reorganization.

### zkApp commands

Successful zkApp commands and their account updates in a block range. This serves an indexer that needs the whole transaction, not only one account's events. Both bounds are required, and `accountPublicKey` keeps only the commands that touch one account. This request returns the Lumina pool's transaction from the events example:

```graphql
query {
  zkappCommands(
    input: {
      from: 470259
      to: 470260
      blockStatus: CANONICAL
      accountPublicKey: "B62qjGGHziBe9brhAC4zkvQa2dyN7nisKnAhKC7rasGFtW31GiuTZoY"
    }
  ) {
    hash
    feePayer
    fee
    memo
    blockInfo {
      height
      stateHash
    }
    accountUpdates {
      publicKey
      tokenId
      authorizationKind
      balanceChange
      callDepth
      events {
        fields
      }
      actions {
        fields
      }
      appState {
        fields
      }
    }
  }
}
```

`balanceChange` is a signed string in nanomina. `appState`, `events` and `actions` are the raw field arrays from the archive database. The query is off by default: set `ENABLE_ZKAPP_COMMANDS_QUERY=true` on the server, and expect a `Cannot query field "zkappCommands"` error from a server that has not.

`kind` is `payment` or `delegation`, and `amount` is `0` for a delegation. `sequenceNumber` is the position of the command in its block. `status` is `applied` or `failed`, and `failureReason` is set only for a failed command. A command that sits in several blocks of the result, such as two competing pending blocks, is returned once for each block, so pass `status: CANONICAL` unless you want the pending chain too.

Both bounds are required. The range may span at most `BLOCK_RANGE_SIZE` blocks, and a range that holds more than `USER_COMMAND_LIMIT` commands for the account (5000 by default) is rejected with a message that says so; halve the range and retry.

The query is off by default: set `ENABLE_USER_COMMANDS_QUERY=true` on the server, and expect a `Cannot query field "userCommands"` error from a server that has not.

:::caution
`userCommands` looks up commands by account through three indexes on the archive's `user_commands` table that Mina's archive schema creates from Mina 5.0.0: `idx_user_commands_fee_payer_id`, `idx_user_commands_source_id` and `idx_user_commands_receiver_id`. Without them the query returns the correct result, but each request reads the whole table. The server logs a warning at startup for each missing index. To add them to a live archive without blocking inserts:

```sql
CREATE INDEX CONCURRENTLY idx_user_commands_fee_payer_id ON user_commands(fee_payer_id);
CREATE INDEX CONCURRENTLY idx_user_commands_source_id    ON user_commands(source_id);
CREATE INDEX CONCURRENTLY idx_user_commands_receiver_id  ON user_commands(receiver_id);
```
:::

### Walk a long history

Range limits differ by query, so a client reads a long history one range at a time.

- `events` and `actions` search at most `BLOCK_RANGE_SIZE` blocks (10000 by default). The server shortens a wider range **without an error**: it keeps `from` and moves `to` to `from + BLOCK_RANGE_SIZE`. With only `to`, it searches the `BLOCK_RANGE_SIZE` blocks below `to`. With neither, it searches the last `BLOCK_RANGE_SIZE` blocks only, so an older event does not appear.
- `verificationKeyUpdates` rejects a range wider than `BLOCK_RANGE_SIZE`.
- `zkappCommands` rejects a range wider than `ZKAPP_COMMAND_RANGE_SIZE` (1000 by default).
- `userCommands` rejects a range wider than `BLOCK_RANGE_SIZE`, and also a range that holds more than `USER_COMMAND_LIMIT` commands (5000 by default) for the account. On the second error, halve the range and retry.

Always send both `from` and `to`, and step `from` by the range size. This TypeScript loop collects every canonical event of an address between two heights:

```ts
const RANGE = 10000; // the server's BLOCK_RANGE_SIZE

const query = `query Events($input: EventFilterOptionsInput!) {
  events(input: $input) { blockInfo { height } eventData { data } }
}`;

async function allEvents(endpoint: string, address: string, fromHeight: number, toHeight: number) {
  const events = [];
  for (let from = fromHeight; from < toHeight; from += RANGE) {
    const to = Math.min(from + RANGE, toHeight);
    const res = await fetch(endpoint, {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify({
        query,
        variables: { input: { address, status: 'CANONICAL', from, to } },
      }),
    });
    const { data, errors } = await res.json();
    if (errors) throw new Error(JSON.stringify(errors));
    events.push(...data.events);
  }
  return events;
}
```

The [client SDKs](#client-sdks) do the request and the retries for you, and the loop stays the same.

## Using it from o1js

A zkApp reaches the API through the `archive` property of its network configuration. o1js then uses it for `fetchEvents` and `fetchActions`:

```ts
const Network = Mina.Network({
  mina: 'https://api.minascan.io/node/devnet/v1/graphql',
  archive: 'https://api.minascan.io/archive/devnet/v1/graphql',
});
Mina.setActiveInstance(Network);
```

Without an `archive` endpoint, fetching events or actions raises an error. For the full o1js workflow, see [Fetch Events and Actions](/zkapps/writing-a-zkapp/feature-overview/fetch-events-and-actions).

## Client SDKs

Typed clients wrap the same endpoint with configurable retries and timeouts. Each has one method for each of `events`, `actions`, `blocks`, `networkState`, `verificationKeyUpdates` and, from SDK 2.1.0, `userCommands`; reach `zkappCommands` and `schemaVersion` through the SDK's raw-query method. An SDK reports the schema it was built for through its `SCHEMA_VERSION` constant (`SchemaVersion` in Go); compare it with the server's `schemaVersion` to know which queries the SDK can wrap.

Pass the server's base URL as-is. The Archive Node API serves GraphQL at `/`, and the SDKs do not append a path.

## Configuration

`PG_CONN` is the only required variable. Configuration is validated at startup: a missing connection string, a non-numeric port, or a mistyped boolean stops the server with a clear message rather than booting into a broken state.

Boolean variables accept `true`/`false`, `1`/`0`, `yes`/`no`, or `on`/`off`, case-insensitively.

### Essentials

| Variable | Default | Description |
|---|---|---|
| `PG_CONN` | *(required)* | Postgres connection string for the archive database |
| `PORT` | `8080` | Port the GraphQL server listens on |
| `BLOCK_RANGE_SIZE` | `10000` | Maximum block span a single query may cover |
| `ENABLED_QUERIES` | *(all)* | Comma-separated subset of root fields to expose. `schemaVersion` is always served |
| `ENABLE_GRAPHIQL` | `false` | Serve the GraphiQL playground at `/` |
| `ENABLE_INTROSPECTION` | `false` | Allow schema introspection |
| `ENABLE_BLOCK_TRANSACTION_DETAILS` | `false` | Include `userCommands`, `zkappCommands`, and `feeTransfers` on blocks |
| `ENABLE_ZKAPP_COMMANDS_QUERY` | `false` | Expose the `zkappCommands` root query |
| `ZKAPP_COMMAND_RANGE_SIZE` | `1000` | Maximum block span of one `zkappCommands` query |
| `ZKAPP_COMMAND_ACCOUNT_UPDATE_LIMIT` | `5000` | Maximum account updates one `zkappCommands` query may expand |
| `ENABLE_USER_COMMANDS_QUERY` | `false` | Expose the `userCommands` root query. Needs the archive's `user_commands` account indexes, see [User commands](#user-commands) |
| `USER_COMMAND_LIMIT` | `5000` | Maximum user commands one `userCommands` query may return |

### Database

| Variable | Default | Description |
|---|---|---|
| `PG_MAX_CONNECTIONS` | `10` | Maximum pooled connections, total rather than per host |
| `PG_IDLE_TIMEOUT` | `30` | Seconds an idle connection is kept |
| `PG_CONNECT_TIMEOUT` | `30` | Seconds to wait for a new connection |
| `PG_STATEMENT_TIMEOUT` | `15000` | Server-side timeout in milliseconds per statement; `0` disables |

For redundancy, `PG_CONN` accepts several hosts — `postgres://host1:5432,host2:5432/archive`, the same syntax `psql` uses. The driver **fails over** between them; it does not spread reads across them.

### Exposure controls

| Variable | Default | Description |
|---|---|---|
| `CORS_ORIGIN` | *(disabled)* | Cross-origin access. Unset means same-origin only; `*` means any origin; or give a comma-separated allowlist |
| `RATE_LIMIT_MAX` | `600` | Requests per client IP per window; `0` disables |
| `RATE_LIMIT_WINDOW_MS` | `60000` | Rate-limit window length |
| `TRUST_PROXY` | *(unset)* | Number of trusted proxy hops in front of the API |
| `GRAPHQL_MAX_DEPTH` | `12` | Maximum selection-set nesting depth |
| `GRAPHQL_MAX_ALIASES` | `15` | Maximum aliases in one operation |
| `GRAPHQL_MAX_TOKENS` | `1000` | Maximum lexical tokens in a query document |
| `GRAPHQL_MAX_COST` | `5000` | Maximum estimated query cost |
| `MAX_REQUEST_BODY_BYTES` | *(off)* | Maximum request body in bytes. A larger declared `Content-Length` gets `413`, and a `POST` without `Content-Length` gets `411`. Set `262144` (256 KiB) on a public deployment |

:::caution
`TRUST_PROXY` has no default, and the rate limiter stays **disabled** until you set it. Neither reading is safe to assume: keying on the socket address behind a load balancer collapses every client into one bucket, while trusting `X-Forwarded-For` without a hop count lets any caller mint a fresh bucket per request. A bare GCP external Application Load Balancer is `TRUST_PROXY=2`; add one per additional proxy. Use `TRUST_PROXY=0` only for a directly exposed server.
:::

:::caution
Browser clients need `CORS_ORIGIN` set. The default sends no permissive CORS headers, so a web front end on another origin cannot call the API until you allowlist its origin. Server-to-server callers and `curl` are unaffected.
:::

The complete reference, including tracing variables, is in the repository's [setup guide](https://github.com/o1-labs/Archive-Node-API/blob/main/docs/getting-started.md#configuration).

## Running it in production

| Endpoint | Purpose |
|---|---|
| `/healthcheck` | Liveness — the process is up and serving HTTP |
| `/readiness` | Readiness — the database is reachable; returns 503 when it is not |
| `/metrics` | Prometheus request-rate, error-rate, and duration metrics, behind `ENABLE_METRICS` |

Point your orchestrator's liveness probe at `/healthcheck` and its readiness probe at `/readiness`, so a pod with an unreachable database leaves the load-balancer pool instead of being restarted.

Two things to keep in mind when you deploy it:

- `/metrics` is unauthenticated. Do not publish it on the same address as the API.
- The query-cost limits bound a query's shape, not its size. Set `MAX_REQUEST_BODY_BYTES=262144` on a public deployment so that one request cannot make the server parse an arbitrarily large body. It is off by default, because turning it on changes what the server accepts.
- On `SIGTERM` the server drains in-flight requests before exiting, bounded by `SHUTDOWN_TIMEOUT_MS` (20000 by default). Keep the orchestrator's grace period above that value or it will kill the process mid-drain.

Reference Kubernetes manifests, a production Compose file, and an operations runbook covering SLOs, capacity, and failover are published in the repository under [`deploy/`](https://github.com/o1-labs/Archive-Node-API/tree/main/deploy) and [`docs/`](https://github.com/o1-labs/Archive-Node-API/tree/main/docs).

## Schema stability

The GraphQL schema follows semantic versioning. A new root field or a new optional argument is a minor release; removing or renaming anything a client can select is a major one, and never happens silently — a schema check gates every change to the repository.

The server, its schema and the client SDKs share one major version. **The same major means compatible**: a 2.x SDK works against any 2.x server, and a higher server minor only adds what the SDK does not wrap yet. Minor and patch versions move independently. Schema 2.1, served from Archive Node API 2.1.0, added the `userCommands` query and nothing else; a 2.0 client keeps working against it.

A client can ask the server which schema it speaks:

```graphql
query {
  schemaVersion
}
```

`schemaVersion` reports the contract, not the queries a given deployment exposes. `ENABLED_QUERIES`, `ENABLE_ZKAPP_COMMANDS_QUERY` and `ENABLE_USER_COMMANDS_QUERY` can still switch data queries off, so detect a missing query from the `Cannot query field` error.

The full policy, including what counts as a breaking change, is in the repository's [versioning guide](https://github.com/o1-labs/Archive-Node-API/blob/main/docs/versioning.md). The 2.1 schema is on the [schema](/node-operators/data-and-history/archive-node-api-schema) page, in the generated [schema reference](/node-operators/data-and-history/archive-node-api/reference/operations), and at `https://docs.minaprotocol.com/archive-node-api/schema.graphql` as a file.
